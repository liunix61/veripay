# VeriPay 总体方案（Solution Overview）

> Arbitrum Open House Singapore Buildathon 参赛项目 #2
> 目标：Overall 前三的 "Arbitrum 链项目" 保底席位（部署 Arbitrum One 主网）
> 与项目 #1 VeriAgent（Robinhood Chain）差异化，共享引擎代码
> 创建：2026-09-13

---

## 1. 一句话定位

**VeriPay = AI Agent 的原生支付轨道**：让 Agent 不再持有用户信用卡/API key，而是用"限额智能账户 + x402 协议"按次付费购买服务，每笔机器消费都有链上收据。

## 2. 解决什么真实问题

**问题**：Agentic commerce（Agent 自主采购数据/API/服务）2026 年爆发，但支付层是空白：

1. **权限过大**：Agent 要付费就得拿到用户完整支付凭证——泄露=无限损失
2. **机器消费无账本**：Agent 花了多少钱、买了什么、给谁，用户事后无法审计
3. **微支付不可行**：传统支付有最低手续费，$0.01 级 API 调用无法用卡结算

**VeriPay 的答案**：
- **限额账户**：每个 Agent 一个智能账户，预算/商户白名单/TTL 由合约硬性限制 → 泄露损失有上限
- **x402 原生**：HTTP 402 机器支付协议，USDC 结算，$0.001 级可行（L2 gas）
- **收据上链**：每笔结算写 ReceiptsRegistry（商户/金额/资源 hash）→ 机器消费可审计

## 3. 与 VeriAgent 的差异化（同场双项目策略）

| 维度 | VeriAgent（项目#1） | VeriPay（项目#2） |
|------|--------------------|--------------------|
| 赛道叙事 | AI Agent 资管原语 | Agent 支付/钱包基础设施 |
| 链 | Robinhood Chain（保底席位 A） | **Arbitrum One 主网**（保底席位 B） |
| 核心合约 | Vault + DecisionRecorder | 限额账户 + 结算 + 收据 |
| 用户 | 投资者 | Agent 开发者/商户 |
| 共享 | engine 引擎、x402 client、前端框架、审计 Explorer 模式 | 同左 |

两个项目互补而非重复。**当前状态**：两项目合约独立部署（VeriAgent 的 PaymentRouter 自带限额路由）；"VeriAgent 金库通过 VeriPay 结算"的组合调用列为赛后组合路线图——demo 时以叙事互相引用，不做硬依赖（避免单项目故障拖垮另一个）。

## 4. 产品形态

```
开发者开 Agent → 部署 AgentPayAccount(预算$50/商户白名单/TTL 30天)
                    │
Agent 运行中调用付费API ←── HTTP 402 + price
Agent 用 session key 签名支付 → Facilitator 验证+结算(USDC on Arbitrum One)
                    │
ReceiptsRegistry 写收据 → 用户面板: 实时消费流水+预算余量
超预算/白名单外/TTL过期 → 合约拒绝，Agent 无法支付
```

三个组件：
1. **AgentPayAccount 工厂**：一键为 Agent 开限额支付账户（ERC-4337 风格但极简自实现）
2. **x402 Facilitator**：开源结算服务（可自托管），验证签名→链上结算→放行数据
3. **消费面板**：Agent 支出流水、预算控制、收据验证

## 8. 社交化扩展：Agent 信号订阅 + 分润（W3 stretch）

**定位**：FOMO 式社交交易的"轻实现"——不做跟单资金盘，做**信号订阅经济**：

```
顶级策略Agent(如VeriAgent的agentId) ──注册为VeriPay商户──→ 发布信号流
粉丝Agent/用户 ──VeriPay订阅付费($1/周)──→ 收到交易信号(买卖/仓位/理由)
订阅费自动拆账: 70% Agent创作者 / 20% 平台金库 / 10% 推荐人
```

- **FOMO 机制**：Agent 实时收益排行榜（数据来自链上 DecisionRecorder，不可刷榜）+ 订阅者数实时显示 + 限时订阅窗口
- **合约增量**：仅 RevenueSplitter（拆账）+ AgentProfile 扩展，复用 ReceiptsRegistry 作为订阅凭证
- **诚信卖点**：排行榜收益全部来自链上决策凭证——"FOMO 但不虚假宣传"，与 VeriAgent 的可验证叙事闭环
- **跟单执行层**（粉丝资金镜像）标为赛后路线图，涉及资金托管合规，比赛期不碰

## 9. V2 路线图：FOMO 跟单社交钱包（赛后，比赛答辩的"资金用途"答案）

**判断**：跟单钱包技术上无鸿沟（Vault 约束 + 镜像执行 + 分润全部有现成积木），比赛期不做是因为资金托管安全工程量大，做糙不如不做。作为 V2 路线图反而是 Promising Products 赛道 "Requesting funding" 评分项的最佳答案。

### V2 核心增量（相对比赛版）

| 组件 | 设计 | 工作量 |
|------|------|--------|
| FollowerVault | 用户存入资金 → 镜像跟随指定策略 Agent，按比例复制其链上交易；进出场走队列防抢跑 | ~2 周 |
| 镜像执行引擎 | 监听 leader DecisionRecorder 事件 → 批量按比例成交 → 滑点保护（偏离阈值拒绝） | ~1 周 |
| 高水位线分润 | 业绩费 10-20%（仅对新高收益部分计提），RevenueSplitter 复用 | ~3 天 |
| 资金安全工程 | timelock + 多签治理 + 退出队列 + 独立审计 + 形式化验证关键路径 | ~3 周 |
| 合规架构 | 分阶段司法辖区评估（收益分成=投顾灰区），先 testnet+限额内测 | 持续 |

### 赛后里程碑

| 阶段 | 内容 |
|------|------|
| M1（赛后 1 月） | FollowerVault + 镜像引擎 testnet 版 + 审计准备 |
| M2（赛后 2 月） | 审计通过 → Arbitrum One 限额公测（单 vault ≤$500） |
| M3（赛后 3 月） | 合规意见 + 正式分润上线 + Base/多链扩展 |

### 答辩话术

"比赛版刻意不碰用户资金托管——限额支付和零托管订阅是我们能审计交付的边界；V2 跟单钱包需要的资金安全工程（审计/多签/退出队列/高水位线会计）就是这笔投资的用途。"

| 风险 | 对策 |
